前置条件

你的 Mac 上必须已安装 Homebrew。

通过 Homebrew 安装

在终端中运行：

brew install claude-code

claude --version

brew upgrade claude-code

好提示与差提示

氛围编程与专业用法之间的差别 — 以我们的 TodoApp 为例：

氛围编程

> add a notes feature

Claude 会随意新建 /api/notes 端点和新 schema，与 models/todo.py 不一致。前端页面也没有侧边栏导航。

模糊、无上下文、无约束。

专业

> 在 backend/routes/todos.py 中新增 PUT /api/todos/{id}/complete 端点。 遵循现有路由模式，并 更新 Todo 模型的 is_completed 字段。 在 tests/test_todos.py 中添加测试。

具体文件、具体端点、具体模式。

提供上下文

关键规则

你给的上下文越多，Claude 表现越好。在提示中用 @ 直接引用文件。

TodoApp 示例

> 查看 @backend/routes/todos.py 与 @backend/models/todo.py 为 Todo 模型增加 priority 字段，并更新 创建端点以接受该字段。

上下文技巧

📄
@file/path指定要让 Claude 读取的文件
📸
粘贴截图Ctrl+V 粘贴报错或界面截图
📋
粘贴错误日志把完整错误信息复制到提示中

上下文窗口与 /compact

核心概念

Claude 有上下文窗口 — 即它能记住的对话量上限。每条提示、每次读文件和每次回复都会占用它。

什么会占用上下文

你的提示与消息

Claude 读取的每个文件

Bash 命令输出

Claude 自己的回复

/compact — 解决办法

> /compact

将对话历史压缩为摘要，Claude 从该摘要继续。

最佳实践

在上下文用量约 50%时手动运行 /compact。不要等到自动压缩 — 那样你会失去对保留内容的控制。

/plan — 先规划再写代码

试一试

> /plan > 为 TodoApp 后端添加用户认证

不用 /plan

Claude 立即写代码

方向错了 — 全部重来

真正开工前已用掉约 50% 上下文

使用 /plan

Claude 以只读方式探索代码库

提出方案供你批准

从一开始就选对方向

经验法则

凡是涉及超过 2–3 个文件或架构决策的任务，都应先用规划模式开始。

规划模式实践

分步操作

# 步骤 1：进入规划模式 > /plan # 步骤 2：描述你的目标 > 为 /api/todos 端点添加分页 # 步骤 3：Claude 探索并写出计划 #（阅读 routes/todos.py、检查模型、提出方案） # 步骤 4：审阅并批准计划 # 随后 Claude 执行已批准的计划

TodoApp 的好处

在规划模式下，Claude 会在写第一行代码之前发现你现有的 SQLAlchemy 分页模式 — 无需重复造轮子。

提示最佳实践

🎯
指明具体文件写「backend/routes/todos.py」而非「后端代码里」
🔎
描述问题本身，而不只说要怎么修写「API 在……时返回 500」而非「帮我弄好」
📐
引用既有模式「按 routes/todos.py 的写法」能给 Claude 模板
🧩
一次只做一件事小而聚焦的请求优于巨型提示
✅
让 Claude 做验证「改完后跑 pytest」能尽早发现问题
📸
界面问题请附截图一图胜千言

第 3 部分

项目记忆

级别：中 — 让 Claude 记住你的项目、约定与偏好。

CLAUDE.md 与 /init

核心概念

CLAUDE.md 是 Markdown 文件，Claude 在每次会话开始时都会读取。它是你给 Claude 的项目说明手册。

创建方式

> /init

TodoApp 的 CLAUDE.md

# CLAUDE.md ## 项目 TodoApp 单体仓库：FastAPI 后端 + Next.js 前端。 ## 结构 - backend/routes/ — FastAPI 路由 - backend/models/ — SQLAlchemy 模型 - frontend/components/ — React 组件 - frontend/lib/api.ts — API 客户端 ## 命令 - cd backend && uvicorn main:app --reload - cd frontend && npm run dev - cd backend && pytest ## 约定 - 后端：遵循 routes/todos.py 中的路由模式 - 前端：使用 Tailwind，新页面加入 Sidebar.tsx - 新端点务必补充测试

CLAUDE.md 里写什么

应包含

项目架构概览

构建与测试命令

关键文件位置

编码约定

应遵循的常见模式

关键的该做与不该做

应避免

整份 API 文档

冗长代码示例

密钥或 API Key

频繁变化的信息

全文超过约 150 行

关键规则

将 CLAUDE.md 控制在150 行以内。过长会稀释指令 — Claude 可能忽略其中部分。细节请用 Rules 与 Skills。

控制在 150 行以内

若需要更多空间

📄
使用 Rules把按主题的说明放在 .claude/rules/*.md
📚
使用 Skills领域知识放在 .claude/skills/ — 按需加载
🔗
引用文件指向文档而非大段粘贴正文

层级关系

CLAUDE.md（始终加载，<150 行）→ Rules（按路径作用域，自动加载）→ Skills（按需，长度不限）。

Rules（.claude/rules/）

什么是 Rules？

分模块、按主题的说明，各自放在独立的 Markdown 文件中。与 CLAUDE.md 不同，规则可以限定到特定路径。

TodoApp 后端测试规则示例

# .claude/rules/backend-testing.md --- globs: ["backend/tests/**"] --- 编写后端测试时： - 使用 pytest 与现有 conftest.py 固件 - 遵循 test_todos.py 中的模式： - 使用 FastAPI 的 TestClient - 用工厂函数创建测试数据 - 同时断言状态码与响应体 - 每个测试后清理测试数据库 - 测试命名：test_{action}_{entity}_{scenario} - 成功与失败路径都要覆盖

该规则仅在 Claude 编辑测试文件时生效 — 其他任务时保持上下文干净。

/memory 与记忆层级

试一试

> /memory

在编辑器中打开你的 CLAUDE.md 记忆文件。在此处的修改会在所有会话中持久保存。

三种作用域（按顺序加载）

# 会话开始时合并加载： ~/.claude/CLAUDE.md # 全局 — 所有项目 .claude/CLAUDE.md # 项目 — 通过 git 与团队共享 .claude/CLAUDE.local.md # 本地 — 个人，git 忽略

TodoApp 提示

将 TodoApp 的 CLAUDE.md 放在仓库根目录，以便整个团队共享。将个人偏好（编辑器、风格等）放在 CLAUDE.local.md 中。

记忆最佳实践

📏
CLAUDE.md 控制在 150 行内简短、聚焦、高信号
📂
细节用 rules在 .claude/rules/ 用路径级规则精准约束
👥
提交项目 CLAUDE.md团队通过 git 共享约定
🔒
个人偏好用 .local.md已 git 忽略，不影响同事
🔄
定期审阅与精简过时说明会造成误解

结构化工作流

级别：中 — 系统化方法，避免白费力气。

任务列表

对于复杂任务，Claude 会创建任务列表以跟踪进度：

> 为 TodoApp 添加用户认证： - POST /api/register 端点 - POST /api/login 端点 - JWT 认证中间件 - 保护 /api/todos 端点 - 覆盖所有认证相关端点的测试

Claude 会将其拆成独立任务，并在逐项完成时展示进度。

最佳实践

将子任务拆到足够小，使每一项都能在50% 上下文以内完成。每完成一个子任务就提交一次。

/model — 模型选择

试一试

> /model

打开模型选择器。让模型与任务相匹配：

🧠
Opus 4.6（默认）复杂任务 — 「为 TodoApp 后端加 JWT 认证」
⚡
Sonnet 4.5日常开发 — 「给 Todo 模型加 completed_at 字段」
🏎
Haiku 4.5简单任务 — 「读 backend/routes/todos.py 并总结端点」

实用技巧

使用 Option+P（Mac）或 Alt+P 快速切换模型。对非复杂任务可使用 /fast 获得更快的 Opus 输出。

工作流最佳实践

🗺
始终先用规划模式任何非琐碎任务都应如此
🧩
把任务拆小每个子任务应在 50% 上下文内完成
💾
每个子任务后提交清晰回滚点，避免巨型单次提交
📦
约 50% 时手动 /compact别等自动压缩
🤖
小任务用原生 Claude Code 即可简单任务不必上复杂工作流

第 5 部分

领域知识

级别：高 — Claude 按需加载的可复用知识。

什么是技能？

核心概念

技能是包含领域知识的 Markdown 文件 — 指令、模式或工作流，Claude 可在需要时加载。可视为微型手册。

为何使用技能？

📚
渐进式呈现仅在相关时加载知识 — 不让每次会话臃肿
♻
可复用同一技能可用于多智能体与工作流
👥
可共享提交到 git — 全团队受益

技能与 CLAUDE.md

CLAUDE.md = 始终加载，每次会话。技能 = 按需加载，在相关时。将「仅有时需要」的知识放在技能中。

创建技能：TodoApp 前端

前端约定技能

# .claude/skills/frontend-conventions/SKILL.md --- name: frontend-conventions description: TodoApp 前端模式与约定 --- # 前端约定 创建或修改前端组件时： ## 侧边栏导航 - 在 frontend/components/Sidebar.tsx 添加新页面路由 - 使用现有 NavLink 模式（图标 + 文案） - 导航项按字母顺序排列 ## 组件模式 - 使用 TypeScript 函数组件 - 从 lib/api.ts 导入 API 函数 - 以 TodoList.tsx 为参考组件 - Tailwind 类名：bg-white、rounded-lg、shadow-sm ## API 对接 - 所有 API 调用经 lib/api.ts - 使用现有 fetch 封装与错误处理 - 基址：process.env.NEXT_PUBLIC_API_URL

技能 Frontmatter 与调用

Frontmatter 选项

📜
name技能标识（省略则用目录名）
📝
description何时调用 — 帮助 Claude 自动发现技能
🤖
model覆盖运行该技能的模型
🔧
allowed-tools限制技能可调用的工具
🔁
context: fork在隔离的子智能体上下文中运行技能（复杂工作流）

调用与执行模式

# 1. 手动：斜杠命令 > /frontend-conventions # 2. 自动：Claude 通过 description 字段发现 # （任务与 description 匹配时触发） # 3. 预加载：写在智能体 frontmatter skills: - frontend-conventions # 4. 可选：复杂工作流使用隔离 context: fork

第 6 部分

代理工程

级别：高 — 了解你的代码库并遵循你的模式的自定义智能体。

什么是智能体？

核心概念

智能体是 .claude/agents/ 中的 Markdown 文件，用于定义具有独立工具、模型、技能与行为的自定义 Claude 人格。

使用智能体的两种方式

作为主智能体

在当前对话中替代默认 Claude。

$ claude --agent frontend-engineer

作为子智能体

通过 Agent 工具在隔离上下文中启动。

Task( subagent_type="frontend-engineer" prompt="添加设置页" )

前端工程师智能体

未使用智能体

> add a settings page

Claude 会创建 pages/settings.tsx，其中包含：

• 内联 CSS（未使用 Tailwind）

• 直接 fetch 调用（忽略 api.ts）

• 无侧边栏导航项

独立页面，与整体应用不协调。

使用智能体

前端智能体已知晓：

• 使用设计系统中的 Tailwind 令牌

• 从 lib/api.ts 导入 API 函数

• 在 Sidebar.tsx 中添加路由

• 遵循 TodoList.tsx 组件模式

与应用完美契合的集成页面。

# .claude/agents/frontend-engineer.md --- name: frontend-engineer description: 遵循 TodoApp 约定的前端开发 tools: Read, Write, Edit, Bash, Glob, Grep model: sonnet skills: - frontend-conventions --- 你是 TodoApp 的前端工程师。 新页面务必加入 Sidebar 导航。 使用 lib/api.ts 中已有的 API 客户端。 以 TodoList.tsx 作为参考组件。

后端工程师智能体

未使用智能体

> add a tags feature

Claude 会随意搭建接口结构

错误处理与现有路由不一致

无测试、无模型校验

使用智能体

后端智能体遵循既有模式：

• 路由结构参考 routes/todos.py

• SQLAlchemy 模型对齐 models/todo.py

• 测试风格与 test_todos.py 一致

• 使用 Pydantic schema 做校验

# .claude/agents/backend-engineer.md --- name: backend-engineer description: 遵循 TodoApp 模式的后端开发 tools: Read, Write, Edit, Bash, Glob, Grep model: sonnet skills: - backend-patterns --- 你是 TodoApp 的后端工程师。 遵循 routes/todos.py 中的路由模式。 创建与 models/todo.py 一致的 SQLAlchemy 模型。 为新端点始终补充 pytest 测试。 使用 Pydantic schema 做请求/响应校验。

智能体 Frontmatter

# .claude/agents/code-reviewer.md --- name: code-reviewer description: 审查代码质量与最佳实践 tools: Read, Grep, Glob model: sonnet color: green skills: - code-review memory: user --- 你是代码审查者。检查安全问题、 性能问题并提出改进建议。 结合记忆中的模式进行审查。

关键字段

🔧
tools智能体能做什么（Read、Write、Edit、Bash 等）
📚
skills启动时预加载的知识
🧠
memory跨会话持久学习（user/project/local）

智能体工具与技能

限制工具

# 只读智能体 — 无法修改任何内容 tools: Read, Grep, Glob # 完全访问智能体 tools: Read, Write, Edit, Bash, WebFetch # 仅研究用智能体 tools: Read, Grep, Glob, WebSearch, WebFetch

核心模式

技能提供静态知识（做什么）。智能体提供执行上下文（如何做、用哪些工具）。二者结合，威力很大。

选择模型

🧠
opus复杂推理与架构决策
⚡
sonnet速度与能力兼顾
🏎
haiku快且省 — 适合简单聚焦任务

通过 Task 工具使用子智能体

核心概念

子智能体在隔离上下文中运行 — 与主对话分离。它们完成任务、返回摘要，随后上下文被丢弃。

# Claude 可自动派生子智能体，也可由你请求： > 使用 frontend-engineer 智能体添加设置页 # Claude 在内部使用 Agent 工具： Task( subagent_type="frontend-engineer", prompt="为 TodoApp 添加用户设置页" )

命令与编排

命令是复杂工作流的入口 — 命令 → 智能体 → 技能 模式：

# .claude/commands/add-feature.md --- description: 为 TodoApp 添加新功能 model: opus --- # 添加功能命令 1. 询问用户要添加什么功能（AskUserQuestion） 2. 调用 backend-engineer 智能体处理 API： - Task(subagent_type="backend-engineer", ...) 3. 调用 frontend-engineer 智能体处理 UI： - Task(subagent_type="frontend-engineer", ...) 4. 运行测试验证：pytest + npm test 5. 总结本次构建内容

如何调用

命令位于 .claude/commands/。用户以斜杠命令调用：> /add-feature

Hooks 与 MCP 服务器

Hooks

在 Claude 生命周期的特定时刻运行的自定义脚本：

16 种钩子事件，其中 5 种可阻塞执行。

+-----------------------------------------------+ | /add-feature （命令） | | 入口 — 用户由此调用 | | | | | +----------+----------+ | | v v | | backend-engineer frontend-engineer | | （智能体） （智能体） | | | | | | backend-patterns frontend-conventions | | （技能） （技能） | +-----------------------------------------------+

命令 = 入口。智能体 = 编排。技能 = 领域知识。职责清晰，复用性最高。

/clear 与 /rewind

/clear — 全新开始

> /clear

彻底清空对话历史。切换任务时使用。

/rewind — 回退

> /rewind

将对话和/或代码回退到更早的状态。

何时用哪个

/clear = 新主题。/rewind = 同一主题但走错了。/compact = 同一主题但上下文吃紧。

提交工作流

让 Claude 提交

> 用清晰的说明提交这些改动

Claude 会：

1️⃣
运行 git status 与 diff审阅已暂存与未暂存改动
2️⃣
起草提交说明强调「为何」而非「改了什么」，并贴合仓库风格
3️⃣
暂存并提交只添加指定文件（非 git add -A）并创建提交

PR 工作流

让 Claude 创建 PR

> 为这些改动创建 Pull Request

Claude 会：

1️⃣
审阅分支上全部提交分析相对基分支的完整 diff
2️⃣
撰写 PR 标题与描述摘要、测试计划与变更概览
3️⃣
推送并通过 gh CLI 创建 PR使用 GitHub CLI 创建 Pull Request

settings.json 概览

设置层级

设置从最具体到最不具体逐级叠加。优先级更高者生效。

# 可写配置覆盖顺序（高到低）： 1. 命令行参数 # --model opus 2. .claude/settings.local.json # 个人，git 忽略 3. .claude/settings.json # 团队共享，已提交 4. ~/.claude/settings.local.json # 全局个人覆盖 5. ~/.claude/settings.json # 全局个人默认 # 策略层： managed-settings.json # 组织策略（强制）

黄金法则

1️⃣
始终先用规划模式任何非琐碎任务都先审计划再让 Claude 写代码。
2️⃣
CLAUDE.md 控制在 150 行内过长会被稀释，细节放 skills 与 rules。
3️⃣
约 50% 时手动 /compact别等自动压缩，自己掌控保留内容。
4️⃣
每个子任务后提交小而频的提交，清晰回滚点。
5️⃣
一次只做一件事小而聚焦的请求优于巨型提示。
6️⃣
指明具体文件写「修 backend/routes/todos.py 第 42 行空值检查」而非「修 bug」。
