# "Vibe Coding 到代理工程"框架

此技能教授演示文稿背后的**概念模型**。每张幻灯片和章节都存在是为了讲述一个故事：开发人员如何从非结构化的"vibe coding"（Low 级别）逐步发展到高级的代理工程（High 级别）。

## 核心概念

**Vibe Coding（Low 级别）**是指开发人员在没有结构的情况下使用 Claude Code — 没有项目上下文、没有约定、没有可重用知识。每个提示都是抛硬币。Claude 可能会创建随机端点、忽略现有模式、跳过测试，并产生不一致的代码。代码库随着每次交互而趋向于熵增。

**代理工程（High 级别）**是指 Claude Code 作为完全配置的工程系统运行。它了解项目架构（CLAUDE.md）、遵循范围约定（Rules）、按需加载领域专业知识（Skills）、委托给专业工作者（Agents）、编排多步工作流程（Commands）、自动化生命周期事件（Hooks），并连接到外部工具（MCP Servers）。每个提示都产生一致的、经过测试的、生产质量的代码。

这两个极端之间的旅程是**渐进式和累积式的**。每个最佳实践都建立在前一个之上，演示文稿按开发人员应该采用它们的顺序进行教学。

## 4 级旅程系统

演示文稿使用 4 级评分系统而非百分比条：

| 级别 | 顺序 | 颜色 | 旅程条高度 | 描述 |
|-------|-------|-------|--------------------|-------------|
| Low | 1 | 红色/橙色（`hsl(0, 70%, 45%)`） | 25% | Vibe coding 领域 — 无结构 |
| Medium | 2 | 黄色（`hsl(40, 70%, 45%)`） | 50% | 结构化工作流程，一些自动化 |
| High | 3 | 浅绿色（`hsl(80, 70%, 45%)`） | 75% | 领域知识、技能、自定义代理 |
| Pro | 4 | 深绿色（`hsl(120, 70%, 45%)`） | 100% | 完整的代理工程，多代理团队 |

旅程条在幻灯片 1（标题幻灯片）上隐藏，从幻灯片 2 开始显示。级别通过关键转换幻灯片上的 `data-level` 属性设置，并由后续幻灯片继承，直到下一次级别变更。当级别变更时，`.level-badge` 由 JS 注入到幻灯片的 `h1` 上（不要在 HTML 中硬编码这些）。

## 运行示例：TodoApp Monorepo

每种技术都在一个现实的全栈项目上进行演示。演示文稿展示了从普通项目（vibe coding）到具有完整 Claude Code 配置（代理工程）的转变：

**之前（Vibe Coding）：**
```
todoapp/
├── backend/          # FastAPI（Python）
│   ├── main.py
│   ├── routes/
│   ├── models/
│   └── tests/
└── frontend/         # Next.js（TypeScript）
    ├── components/
    ├── pages/
    └── lib/
```

**之后（代理工程）：**
```
todoapp/
├── .claude/                  # Claude Code 配置
│   ├── agents/               # 自定义子代理
│   ├── skills/               # 领域知识
│   ├── commands/             # 斜杠命令
│   ├── hooks/                # 生命周期脚本
│   ├── rules/                # 模块化指令
│   ├── settings.json         # 团队设置
│   └── settings.local.json   # 个人设置
├── backend/
│   └── CLAUDE.md             # 后端指令
├── frontend/
│   └── CLAUDE.md             # 前端指令
├── .mcp.json                 # 托管 MCP 服务器
└── CLAUDE.md                 # 项目指令
```

**为什么选择 TodoApp？**它足够小可以放在幻灯片上，但又足够复杂可以演示真实问题：一个具有路由模式和测试约定的后端、一个具有组件层次结构和设计令牌的前端，以及一个 monorepo 结构，其中跨领域问题（如添加新功能）需要双方协调。

TodoApp 使 vibe-coding 问题具体化：没有结构，要求 Claude"添加笔记功能"会产生一个随机的 `/api/notes` 端点，它不遵循 `routes/todos.py` 模式，一个没有侧边栏导航的独立页面，以及零测试。通过完整的代理设置，同样的请求会产生遵循现有模式的路由、集成到侧边栏的页面，以及与 `test_todos.py` 样式匹配的测试。

## 旅程弧线：为什么是这个顺序

演示文稿遵循深思熟虑的教学顺序。每个章节解锁一个新的能力层：

### 第 0 部分：介绍（幻灯片 1–4，无权重）
**目的：**设定舞台。介绍 TodoApp，定义 vibe coding，并展示目的地。
- 标题幻灯片建立旅程隐喻
- 示例项目展示转变：TodoApp 的前后对比 — 普通项目结构与具有完整 Claude Code 配置（.claude/、CLAUDE.md、.mcp.json 等）的项目
-"什么是 Vibe Coding？"创建 0% 基线 — 痛点
- 旅程地图提供可点击的 TOC，显示前方的完整路径

### 第 1 部分：先决条件（幻灯片 5–9，无权重）
**目的：**安装并运行 Claude Code。这纯粹是后勤工作 — 还没有工程实践。
- 安装、身份验证、首次会话、界面概述
- 无权重，因为知道如何安装工具不会提高代码质量
-"首次会话"就是 vibe coding — 这是故意的，以便开发人员亲身体验 0% 状态

### 第 2 部分：更好的提示（幻灯片 10–17，级别：Low）
**目的：**第一次真正的改进。更好的输入产生更好的输出，即使没有任何项目配置。
- **好与坏的提示：**具体、有范围的提示与模糊请求。最简单的改进。
- **提供上下文：**使用 `@files` 向 Claude 提供它需要的代码。立即减少幻觉。
- **上下文窗口和 /compact：**理解有限的上下文窗口可防止长会话中响应降级。
- **计划模式：**`/plan` 在编码前强制思考。防止在错误方法上浪费精力。

**为什么是 Low 级别：**提示是基础但有限的。它改进了单个交互，但不会创建持久的项目知识。每个会话都从零开始。

### 第 3 部分：项目记忆（幻灯片 18–24，级别：Medium）
**目的：**从会话级别跃升到项目级别知识。Claude 现在可以跨会话记忆。
- **CLAUDE.md 和 /init：**项目的"Claude 的 README"。建立架构、技术栈和约定。这是单个最具影响力的文件。
- **包含什么：**编写有效 CLAUDE.md 内容的实用指南（保持在 150 行以下，专注于 Claude 需要知道的内容）。
- **规则：**`.claude/rules/` 中的路径范围约定。规则是乘数 — 它们自动应用于每个匹配的文件，无需开发人员努力即可强制执行一致性。单个 `backend-testing.md` 规则确保每个测试永远遵循相同的模式。

**为什么是 Medium 级别：**项目记忆将 Claude 从无状态工具转变为上下文感知的协作者。但仅有知识不会创建工作流程。

### 第 4 部分：结构化工作流程（幻灯片 25–28，级别：Medium）
**目的：**防止浪费精力并提高执行质量的系统方法。
- **任务列表：**将复杂工作分解为可跟踪的步骤。防止范围蔓延并确保完整性。
- **模型选择：**选择正确的模型（Opus 用于架构、Sonnet 用于实现、Haiku 用于快速任务）优化成本和质量。

**为什么仍然是 Medium 级别：**工作流程很重要但相对简单的概念。它们建立在第 3 部分的项目记忆之上，并更系统地使用它。升级到 High 伴随着领域知识。

### 第 5 部分：领域知识（幻灯片 29–33，级别：High）
**目的：**可重用的按需专业知识。技能是静态记忆（CLAUDE.md/Rules）和动态代理之间的桥梁。
- **什么是技能：**技能作为 Claude 在相关时加载的打包领域知识。渐进披露的概念。
- **创建技能：**实践：为 TodoApp 构建 `frontend-conventions` 技能，教授 Tailwind 令牌、组件模式和侧边栏集成。
- **技能 Frontmatter 和调用：**技术细节：YAML frontmatter、手动与自动发现调用、`context: fork` 选项。

**为什么是 High 级别：**技能是第一个"乘数"概念 — 一个技能定义改进其领域中的每个未来交互。但技能是被动知识；它们需要代理才能变得主动。

### 第 6 部分：代理工程（幻灯片 34–46，级别：High）
**目的：**本演示文稿涵盖的目的地。协调构建端到端功能的自主、专业化代理。
- **什么是代理：**具有受限工具和预加载技能的专业化子代理的概念。
- **前端工程师代理：**使用 TodoApp 前端约定、将路由添加到侧边栏、遵循设计令牌的具体代理。前后对比展示了转变。
- **后端工程师代理：**后端的并行代理 — 遵循 FastAPI 路由模式、SQLAlchemy 模型、编写与现有样式匹配的测试。
- **命令和编排：**顶点模式：命令 → 代理 → 技能。单个 `/add-feature` 命令协调前端 + 后端代理，每个代理都有自己的技能，以交付完整功能。这是架构的顶峰。
- **Hooks 和 MCP：**生命周期自动化（预提交检查、声音通知）和外部工具集成。最后的自动化层。
- **命令 → 代理 → 技能：**完整的架构图。展示所有部分如何连接：命令调用代理、代理加载技能、技能提供知识。这是"High 级别"理解幻灯片。

**为什么是 High 级别：**本节涵盖本演示文稿中教授的最高价值实践。之前的一切都是朝着这个目标建设的。编排和代理工作流程代表了本课程涵盖内容的上限 — 完整的 Pro（多代理团队、高级编排模式）超出了本演示文稿的范围。

### High 级别幻灯片（幻灯片 44）
庆祝时刻。展示完整的 TodoApp 配置：
- CLAUDE.md 用于项目上下文
- Rules 用于路径范围约定
- Skills 用于领域知识
- Agents 用于一致执行
- Commands 用于编排工作流程
- Hooks 用于生命周期自动化
- MCP servers 用于外部工具

### 附录（幻灯片 47+，无权重）
**目的：**参考资料。每个命令、设置和配置选项。无权重，因为这些是参考查找，而非旅程里程碑。包括：工具使用、所有斜杠命令、提交/PR 工作流程、自定义选项、调试技巧和黄金规则。

## 编辑幻灯片时如何使用此框架

创建或修改幻灯片时，考虑：

1. **这个概念在旅程中处于什么位置？**关于"提示中更好的错误消息"的幻灯片属于第 2 部分（提示，Low 级别）。关于"代理内存范围"的幻灯片属于第 6 部分（代理，High 级别）。

2. **前后对比是什么？**每张重要的幻灯片都应该隐式或显式地展示对比：在 Low 级别（vibe coding）会发生什么与使用此技术会发生什么。使用 TodoApp 使其具体化。

3. **级别分配感觉对吗？**级别转换发生在部分章节边界。章节内的单个幻灯片继承章节的级别。

4. **它是否建立在之前的基础上？**技能假设开发人员已经了解 CLAUDE.md 和 Rules。代理假设他们了解技能。命令假设他们了解代理。永远不要在其章节之前引用概念。

5. **使用 TodoApp。**抽象解释会失去观众。展示实际的 `routes/todos.py` 代码、实际的 `Sidebar.tsx` 组件、实际的 `CLAUDE.md` 内容。运行示例是使框架具体化的关键。

所有其他幻灯片从它们之前设置的最后一个 `data-level` 属性继承级别。幻灯片 1–9（介绍 + 先决条件）没有级别，并保持条隐藏，直到幻灯片 2 显示"Low"（幻灯片 2–9 在幻灯片 10 的第一个级别转换之下，因此条显示空/零，直到幻灯片 10）。

**注意：**主演示文稿（`presentation/index.html`）上限为 **High** 级别 — 不使用 `data-level="pro"`。Pro 刻度标记在旅程条上保持可见作为理论上限，但填充永远不会达到它。视频演示文稿（`1-video-workflow.html`）上限为 **Medium** 级别。
